# 个人知识库建设计划

目标是把工作中的进展、收获、技术问题和专业术语持续沉淀下来，做到遇到相似问题时能快速找到已有结论，并能将成熟内容整理成博客文章。先建立稳定的记录习惯和内容规范，再接入博客展示层。

当前仓库已有 22 篇文章，涵盖面试、学习教程和个人项目，另有文章图片。本阶段保留这些内容的路径，补充记录入口、目录规范和写作模板；后续按实际使用情况逐步整理。

## 一 内容如何积累

内容按用途分为三层，具体目录见[目录结构与写作规范](directory-design.md)。

| 层次 | 内容与位置 | 解决的问题 |
| --- | --- | --- |
| 时间记录 | `journal/` 中的每日记录、每周复盘 | 我做了什么，产生什么结果，还有什么阻塞 |
| 长期知识 | `knowledge/` 中的专题笔记、问题方案、术语卡片 | 原理是什么，相似问题如何处理，适用边界是什么 |
| 博客文章 | `posts/` 中的教程、面试整理、项目实践 | 如何向不了解上下文的读者讲清楚一个问题 |

日常记录是素材入口，长期知识是可复用结论，博客文章是面向读者的表达。一篇知识正文只维护一份，其他位置写简要结论并链接到它。成熟笔记可以直接作为公开知识页；需要教程化表达时再形成文章，避免复制出两份相同正文。

例如，排查了一次 Redis 缓存问题，可以这样记录：

1. 日报记下问题影响、当天进展和下一步。
2. 问题方案保存环境、排查证据、根因、修复和验证过程。
3. 术语卡片解释首次遇到的“缓存击穿”，并链接到问题方案。
4. 周报总结处理结果和仍需跟进的风险。
5. 有可推广的经验时，整理成面向读者的文章，并引用原有笔记。

## 二 成熟博客与知识库参考

借鉴以下已成熟的组织方式，当前内容格式保持独立，框架在建站阶段再确定。

| 参考 | 可以借鉴的设计 | 本仓库的落点 |
| --- | --- | --- |
| [PaperMod 官方博客示例](https://adityatelange.github.io/hugo-PaperMod/archives/) | 提供归档、搜索、标签入口，归档按年和月组织 | 日周记录按时间存放，未来博客提供按年月回顾和标签检索 |
| [Quartz 目录与标签索引](https://quartz.jzhao.xyz/features/folder-and-tag-listings)及[反向链接](https://quartz.jzhao.xyz/features/backlinks) | 目录页组织主题，标签连接跨主题内容，反向链接展示引用关系 | 知识按主题归类，用标准 Markdown 链接串联记录、术语和方案 |
| [Astro 官方博客模板](https://github.com/withastro/astro/tree/main/examples/blog)及[内容集合](https://docs.astro.build/en/guides/content-collections/) | 博客正文与页面、布局分开，内容集合组织 Markdown 和元数据 | 现在统一正文格式，后续让展示层读取现有内容，适配字段和路由 |
| [VitePress 文件路由](https://vitepress.dev/guide/routing) | Markdown 路径映射到页面路径 | 保持文件命名稳定，移动文章时同步检查链接和公开地址 |

本方案建议未来博客采用“文章、知识库、周记、归档、标签、关于”作为主导航，搜索作为全局入口。首页展示近期文章和少量主题入口；知识库页按技术主题导航；正文页显示摘要、日期、目录、相关术语与方案。只显示已公开的内容，空分类暂不展示。

## 三 日常与每周如何执行

### 每天简记再每周整理

适合工作日能留出少量时间的情况。建议每日投入 5 至 10 分钟，每周再集中整理 30 至 45 分钟，时间仅作为起步参考。

| 时间 | 做什么 | 最小产出 |
| --- | --- | --- |
| 工作结束前 | 用[每日模板](../templates/daily.md)记录成果、阻塞、收获和下一步 | 一条可核对的进展、一条收获或问题，没有则如实省略 |
| 遇到有复用价值的问题时 | 先记环境与证据，再补充[问题方案](../templates/solution.md) | 现象、当前结论、验证结果或待验证项 |
| 周五或周末 | 用[每周模板](../templates/weekly.md)回顾结果，整理知识和下周重点 | 一份周报，按实际情况整理 1 至 2 条值得保留的知识 |
| 每月末 | 用约 30 分钟复查过时结论、重复笔记和文章候选 | 更新重要知识，选择下一篇值得写的文章 |

忙碌时只记“完成事项、关键问题、下一步”三项，细节周末补充。没有新术语、没有值得整理的方案时，不为凑数量创建卡片。

### 每周集中整理

如果每天记录难以坚持，可以只维护周报：工作中临时材料留在本地，周末用 30 至 60 分钟整理成果、收获、问题与下周安排，再按需提炼知识。无需补写没有实际价值的历史日报。

### 记录质量要求

- 工作进展写“完成了什么、结果如何、下一步是什么”，未完成事项注明卡点和下次检查时间。
- 技术难题区分观察到的事实、排查假设和验证后的结论；尚未确认根因时保持草稿并说明缺少什么证据。
- 解决方案记录版本、前提、关键步骤、验证方式和适用边界；临时绕过与长期修复分别说明。
- 技术收获用自己的话解释，并尽量关联一个实际场景；官方文档标明链接与查阅日期，易变信息保留版本。
- 术语写中文名、英文全称、缩写、直观例子及易混概念；常用术语持续更新同一张卡片。

公司、客户、账号、内部地址、业务数据和未脱敏截图等原始材料留在本地 `private/`，再提炼可公开知识。该目录已被 Git 忽略，需要单独备份；忽略规则不会清除已跟踪文件或历史记录。即使标记为 `private`，进入可跟踪目录的文本也可能被仓库读者访问。

## 四 四周落地安排

以下目标可按实际工作量调整，先验证记录方式是否能持续使用。

| 阶段 | 主要动作 | 完成标准 |
| --- | --- | --- |
| 第一周 建立入口 | 使用六类模板，选择每日或每周节奏，只为真实内容创建目录 | 完成首份周报，能明确判断一条内容该放在哪里 |
| 第二周 沉淀知识 | 从记录中提炼真实问题和术语，补全来源、版本、证据与链接 | 至少形成一份可复用方案；没有合适问题时整理一份专题笔记 |
| 第三周 整理存量 | 优先选择常查或近期使用的 3 至 5 篇文章，逐篇复核知识与元数据 | 标记待更新内容，补全文章入口；已失效的结论注明替代方案 |
| 第四周 准备博客 | 选出 1 至 2 篇成熟内容，检查脱敏、摘要、链接与发布地址 | 形成公开候选清单，并确认博客框架与内容接入方案 |

当前已提供计划、目录规范、入口说明与六类模板，22 篇现有文章已补齐分类、主题、标签和元数据，并建立[文章索引](../posts/README.md)与[检查记录](content-audit.md)。文章仍保持草稿，技术事实按实际需要继续逐篇复核。日期和主题示例在真实写作时创建，记录内容与博客工程按上述阶段逐步补充。

存量整理建议从 `posts/my-projects/` 和 `posts/learning/` 开始，再处理常用面试主题。`posts/interview/` 可以继续作为面试索引；其中值得长期维护的原理，提炼到 `knowledge/notes/` 后以链接关联，逐步减少重复正文。

## 五 后续转为个人博客

### 框架选择

按博客为主的目标，建议先评估 Astro 官方博客模板和 Hugo PaperMod；如果后续更看重知识关联和反向链接，再评估 Quartz。以专题手册为主时可考虑 VitePress，其文章归档与标签入口需按博客需求组织。上述取舍是基于本仓库目标的建议，并非已经完成框架选型。

Astro 的内容加载器可以读取指定目录，后续可接入现有 Markdown，减少为适配站点而搬动文件的工作。[Astro 内容加载器文档](https://docs.astro.build/en/guides/content-collections/#the-glob-loader)

### 接入顺序

1. 在后续新增的 `site/` 中维护展示层和框架配置，正文继续以现有目录为源；框架要求不同位置时，在内容接入层映射，不维护两份正文。
2. 使用人工确认的公开候选清单接入首批文章，补齐元数据并映射框架字段；现有文章缺少发布字段时默认排除。
3. 统一生成正文页、归档、标签、搜索、RSS 和站点地图，所有出口使用同一份可发布内容集合。
4. 仅复制已公开内容引用的可公开资源，验证内部链接、图片、代码块、中文标题和窄屏阅读。
5. 本地预览核对公开范围和页面效果，选择托管平台后再执行首次发布。

公开条件统一为：来源属于明确允许的内容目录，且 `visibility: public`，且 `status` 为 `ready` 或 `published`。`docs/`、`templates/`、目录说明文件和 `private/` 不进入博客内容集合。默认仅接入 `posts/`，知识页或周记需另行加入允许范围；每日记录默认不发布。发布规则的字段与资源处理细节见[目录规范](directory-design.md)。

`status`、`visibility`、`summary` 等字段属于仓库自己的约定，需要在展示层明确适配。本阶段只制定规则，尚未实现网站过滤或部署能力。

### 存量迁移重点

- 现有部分文章在元数据开头前有空行，部分 `title` 含编号和 `.md`；接入博客前逐篇修正，不批量改动整库。
- 保留原始 `date`，更新内容时补充 `updated`；文章文件名前的编号不自动成为公开地址。
- 为公开内容确定唯一且稳定的 `slug`。已公开文章移动目录时，保持地址或设置重定向，并同步检查文章互链和图片。
- 复核技术结论、版本和外部链接；存量文章不因所在目录是 `posts/` 就视为已审核。

## 六 如何判断计划有效

连续使用四周后，检查三个实际结果：能在一分钟左右找到近期解决过的问题；方案包含足够信息供未来复现和判断边界；至少有一篇内容无需补回工作上下文就能让其他读者理解。

如果整理耗时过多，优先缩减日报栏目和卡片数量，保留每周复盘与高价值方案。如果检索仍然困难，先修正标题、主题归属、标签和关联链接，再考虑增加目录层级或工具。
