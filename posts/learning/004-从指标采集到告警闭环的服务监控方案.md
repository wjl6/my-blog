# 从指标采集到告警闭环的服务监控方案

服务故障经常先表现为请求变慢、任务积压，最后才变成接口不可用。只检查进程或 HTTP 状态码，会错过磁盘增长、提交受阻和后台任务停止推进等信号。

一套可用的监控方案需要回答四件事：采集是否可信，业务能力是否正常，谁应在什么时间处理，以及怎样确认恢复。下面以 Prometheus、Grafana 和 Alertmanager 组成的独立平台展开；阈值、目标名称与路径均为模拟示例，验收表说明预期行为，不代表已完成生产演练。

## 一 让监控跨出业务系统的故障域

如果看板登录、目标配置查询、告警队列和发信全部依赖业务数据库，数据库故障可能同时带走监控入口。监控平台应有独立的数据目录、账号和通知配置；关键告警直接交给通知组件处理，不经过业务消息队列。

三个组件的职责可以保持清楚：

| 组件 | 负责什么 | 需要额外验证什么 |
| --- | --- | --- |
| Prometheus | 抓取指标、保存时间序列、评估告警规则 | 目标是否完整，规则是否持续执行 |
| Grafana | 展示趋势、筛选对象、连接排障入口 | 缺数是否被错误映射成正常 |
| Alertmanager | 告警分组、抑制、静默和通知 | SMTP、收件人、恢复通知是否有效 |

Prometheus 规则产生告警，Alertmanager 管理通知，这是该架构的基本职责划分。[Prometheus 告警流程](https://prometheus.io/docs/alerting/latest/overview/)

首期可以用独立部署的现成看板满足技术人员排障。若以后需要业务系统内置入口，再接入简化视图；独立平台仍应能在业务登录服务故障时访问。数据源和看板可以通过配置文件管理，便于审查、迁移与回退。[Grafana 配置交付](https://grafana.com/docs/grafana/latest/administration/provisioning/)

## 二 按故障机制确定采集范围

采集对象不能只列组件名称，还应写明它可能怎样失败，以及哪个信号能提前发现。

| 层次 | 关键观察 | 对应判断 |
| --- | --- | --- |
| 主机与文件系统 | 可用字节、inode、只读状态、I/O 延迟 | 是否还能写入，剩余处置时间是否足够 |
| MySQL | 连接容量、提交耗时、长事务、锁等待、binlog 规模 | 服务可连接时，事务是否仍能推进 |
| MQ、Redis、搜索服务 | 消费延迟、积压、持久化结果、分片及资源状态 | 是否正在丢失处理能力或逼近资源边界 |
| 应用与异步任务 | 请求失败率、延迟、最老可处理任务年龄、成功轮询时间 | 请求和后台处理是否持续取得进展 |
| 外部模型与 OCR | 模拟请求结果、结构有效性、耗时、错误类别 | 当前启用能力是否实际可调用 |

连接成功只能证明一部分路径可达。只读数据库探测不能证明提交成功，MQ 端口可连接也不能证明消费正在推进。对于延迟执行任务，应从积压指标中排除尚未到执行时间的项，避免把正常等待误报为故障。

采集查询同样消耗资源。数据库统计优先利用状态索引、只返回聚合值，并设置查询超时与执行周期；不要为监控全表加载历史任务，更不要读取业务正文。对暂时无法取得的主机权限或依赖指标，应明确显示覆盖缺口。

## 三 区分故障、缺数与数据过期

Prometheus 的 `up=1` 表示该次抓取成功，`up=0` 表示抓取失败。即使 Exporter 正常响应，它观察的数据库、模型或业务操作仍可能失败。[Prometheus 的 up 指标](https://prometheus.io/docs/concepts/jobs_instances/)

看板至少区分正常、异常、未知、未接入和维护状态。自定义检查需要同时提供结果和检查时间，不能让昨天的成功结果一直显示绿色。可使用固定类别的错误码，区分超时、鉴权失败、连接失败和响应不符合约定。

下面两个表达式解决不同问题，示例目标完全虚构：

```promql
up{job="demo-node"} == 0
```

它检查仍在抓取清单中的失败实例。若目标被误删，时间序列最终消失，不能指望这条规则继续报错。

```promql
absent_over_time(
  up{job="demo-node", instance="demo-node-01"}[6m]
)
```

第二条只检查这个预先指定的实例在窗口内是否完全无样本。它不会自动枚举所有消失的实例；对多个动态目标，应维护预期目标清单并逐目标对照，或者生成对应的缺失规则。[PromQL 缺失检测](https://prometheus.io/docs/prometheus/latest/querying/functions/#absent_over_time)

还需区分“最近检查过但失败”和“检查器本身停止工作”。例如最近成功时间长期不变，可能是连续失败；最近检查时间也不再更新，才指向检查链路停滞。告警应保留这两类原因。

## 四 磁盘告警先找对挂载点再预测增长

数据库对象体积无法反推出文件系统可用空间。先建立数据目录、binlog、临时文件、备份和容器日志到实际挂载点的对应关系；不同目录可能共用同一个卷。

Node Exporter 采集宿主机指标。采用容器部署时，需要正确暴露宿主机命名空间和挂载范围，否则可能看到采集器容器自己的文件系统。[Node Exporter 容器部署说明](https://github.com/prometheus/node_exporter#docker)

binlog 规模则由数据库侧补充。`mysqld_exporter` 的 `collect.binlog_size` 能统计已登记二进制日志的总量，但它不能代替主机剩余空间。[MySQL Exporter 采集项](https://github.com/prometheus/mysqld_exporter#collector-flags)

容量告警可以分成三层：空间或 inode 已不足、文件系统只读或不可写、预计耗尽时间已短于响应与处置预算。最后一层用于提前行动，前两层保留为直接风险信号。

下面是模拟挂载点的趋势表达式：以两小时样本预测八小时后的可用字节，并要求当前剩余比例低于四分之一。它是规则片段，不是完整告警配置。

```promql
(
  predict_linear(
    node_filesystem_avail_bytes{
      job="demo-node", mountpoint="/demo-data"
    }[2h],
    8 * 3600
  ) < 0
)
and
(
  node_filesystem_avail_bytes{
    job="demo-node", mountpoint="/demo-data"
  }
  / node_filesystem_size_bytes{
    job="demo-node", mountpoint="/demo-data"
  } < 0.25
)
```

`predict_linear` 适用于 Gauge，使用线性回归预测未来值；数学上至少需要两个浮点样本，工程上还应验证采样覆盖率。[PromQL 线性预测](https://prometheus.io/docs/prometheus/latest/querying/functions/#predict_linear)

日志清理、扩容和突发写入都会改变趋势，样本不足或预测得到 `NaN` 时不能当作安全。预测适合提示风险，不能替代实时阈值、只读状态检查和人工容量判断。阈值应从实际处置时间推导，再通过模拟数据评估误报与漏报。

## 五 将 AI 探测与指标抓取解耦

AI 服务至少包含三层健康含义：进程能够响应、依赖和当前路由已就绪、固定模拟输入能够得到符合约定的结果。普通健康接口适合频繁检查前两层，低频合成探测验证第三层。

合成探测使用重新构造的短文本、图片或固定测试对象，不创建真实业务任务，不读取生产内容，也不触发业务回调。HTTP 成功后仍要校验响应结构、必填结果和结束状态；返回空内容或格式错误应计为失败。

高成本调用不应绑在每次 `/metrics` 抓取上。后台探测按目标去重，限制并发、超时和重叠执行，将结果缓存为指标；抓取只读取缓存。当前路由与已启用备用能力应分别标识，避免只测备用端点却误判实际路径正常。

探测预算可按“目标数量 × 每日轮次 × 单次最大成本”估算，并记录失败重试产生的额外开销。客户端超时不证明远端处理已经停止，因此不能无限重试，也不能把超时自动视作没有计费。探测周期较长时，通知延迟自然增大，应在服务等级约定中体现。

## 六 把告警变成可执行的通知

规则必须同时具有故障对象、严重级别、持续条件和处置入口。Prometheus 的 `for` 表示表达式在连续评估中保持成立的时间，用于控制短暂波动；它不能替代采集缺失检测。[Prometheus 告警规则](https://prometheus.io/docs/prometheus/latest/configuration/alerting_rules/)

通知延迟由探测周期、采集与评估周期、`for`、分组等待和邮件投递共同决定。SMTP 故障或重试还会继续延长，不能仅根据“每分钟检查”承诺一分钟内收到邮件。

Alertmanager 负责合并相同故障的重复通知。`group_wait` 控制新组首次等待，`group_interval` 控制已有组变化通知的节奏，`repeat_interval` 控制持续故障的重复提醒。邮件恢复通知需要在 `email_configs` 中显式配置 `send_resolved: true`，其默认值为 `false`。[Alertmanager 路由与邮件配置](https://prometheus.io/docs/alerting/latest/configuration/)

抑制应限制在明确的共同故障对象内。例如同一主机的严重容量告警可以抑制对应低级别预警，但不能用“任意主机宕机”压住整个环境的异常。参与匹配的对象标签必须完整，避免缺失标签使无关告警被归为同组。

一封邮件应让值班人员直接判断下一步，至少包含环境、服务、首次发生时间、当前值与阈值、影响说明、排查步骤和看板链接。收件人和阈值可由受控运维配置维护；SMTP 凭据单独保管，不写入仓库。通知服务接受邮件并不代表收件箱已收到，投递验收要走完实际收件链路。

## 七 单独验证监控平台自身

Prometheus 停止评估时，无法靠它自己的规则宣布自己停止。需要另一个故障域观察新心跳是否持续到达，并拥有能够独立工作的通知路径；同一主机上的另一个容器不足以覆盖整机故障。

外部检查既要验证心跳的新鲜度，也要覆盖 Prometheus 到 Alertmanager 的链路。主平台反向检查外部检查器，避免辅助组件长期失效。若两者共用同一 SMTP，仍有共同通知故障，应按可接受风险增加其他通知通道或独立投递依赖。

监控自身还需要容量预算：时间序列保留时间、存储大小限制、容器日志轮转和磁盘余量共同管理。保留限制不能理解成任何时刻都绝不会占满空间，仍需监测实际磁盘。[Prometheus 存储说明](https://prometheus.io/docs/prometheus/latest/storage/)

## 八 分阶段落地并按失败场景验收

第一阶段先接入主机、关键依赖和邮件闭环，解决故障发现；第二阶段补齐事务、任务进度和 AI 合成探测；第三阶段再完善趋势预测、通知收敛和外部心跳。每阶段都明确哪些对象已覆盖，哪些仍是未知状态。

| 隔离环境中的模拟故障 | 预期验收结果 |
| --- | --- |
| 目标断连、鉴权失败或从清单误删 | 分别产生失败或缺失信号，不能显示恢复 |
| 注入低空间、inode 耗尽或只读样本 | 对应规则触发，并指向正确挂载点 |
| 业务进度停止但进程保持在线 | 任务年龄或进度规则发现停滞 |
| 模型超时、空结果或响应结构错误 | 合成探测失败，调用次数保持在预算内 |
| 同一故障连续触发与恢复 | 分组、抑制、提醒及恢复邮件符合约定 |
| 停止主监控或外部检查器 | 另一侧能够识别相应链路中断 |

先通过隔离收件服务验证通知内容，再由授权人员确认指定邮箱的实际投递。磁盘规则使用模拟时间序列或隔离测试卷验证，不能通过填满生产磁盘或清理生产日志制造测试条件。

交付时固定组件和采集器版本，用对应版本校验配置及规则；变更失败保留上一份有效配置。采集账号按启用采集项授予最小权限，管理和指标接口限制访问范围。

标签只使用受控维度，例如环境、服务、实例和错误类别。请求 ID、用户信息、完整 URL 或异常原文不应进入指标标签，否则既增加隐私暴露，也使时间序列数量随请求持续增长。[Prometheus 标签设计建议](https://prometheus.io/docs/practices/instrumentation/#do-not-overuse-labels)

监控是否可用，最终由失败场景决定：故障能被及时发现，通知能送达可行动的人，恢复经过同样严格的检查，才形成完整闭环。
