# 医药行业计算机化系统验证（CSV）：定义、规范与文件写法

计算机化系统验证（Computerized System Validation，CSV）是为特定的**预定用途**建立并维护证据的过程。它要证明系统在所批准的环境和控制条件下能可靠地完成规定工作，保护相关记录，并让使用方在软件升级、配置变化或数据迁移后仍能判断系统是否适用。以药品生产质量管理（GMP）为例，应用程序需要验证，支撑它的 IT 基础架构需要确认，工作深度由书面风险评估决定。[中国 GMP 附录《计算机化系统》](https://www.tid.gov.hk/en/tradecircular/files/2015/ci2015512a.pdf) · [欧盟 GMP Annex 11](https://health.ec.europa.eu/system/files/2016-11/annex11_01-2011_en_0.pdf)

本文用一个完全模拟的电子质量记录系统说明写法。文件名称、编号和示例角色都是便于理解的约定；正式项目由适用规范和企业质量体系决定审批职责、模板和证据保存方式。

## 一 先判断法规适用和系统边界

从受监管的活动出发：系统产生、修改或传输哪些记录？谁依据这些记录作决定？如果记录错误、不可用或无法追溯，会影响什么？再列出软件版本、配置、角色、基础设施、外部接口、数据迁移与人工步骤，说明哪些纳入验证、哪些排除以及理由。系统可以是自研、采购或托管；供应商的报告可评估后复用，使用方仍须证明自己的配置、接口和业务场景适用。

| 依据 | 对应范围与用法 |
| --- | --- |
| 中国《药品生产质量管理规范》及《计算机化系统》《确认与验证》附录 | 用于药品生产质量管理。GMP 正文第 147 至 148 条规定方案审批、按批准方案执行、结果报告及存档。2015 年第 54 号公告的两份附录进一步规定风险评估、使用前测试、持续控制和偏差处理。参见[总局 GMP 正文](https://www.samr.gov.cn/zw/zfxxgk/fdzdgknr/bgt/art/2023/art_d5e1dbaa8f284277a5f6c3e2fc840d00.html)及[公告和附录全文](https://www.tid.gov.hk/en/tradecircular/files/2015/ci2015512a.pdf)。 |
| 欧盟 EU GMP Annex 11 与 Annex 15 | Annex 11 涵盖 GMP 计算机化系统的生命周期、需求追溯和数据控制；Annex 15 说明确认与验证方案、接受标准及阶段审批。欧委会目录列出的 Annex 11 为 2011 年版；公开征求意见的修订稿不能当作现行正文。见[现行目录](https://health.ec.europa.eu/medicinal-products/eudralex/eudralex-volume-4_en)、[Annex 15](https://health.ec.europa.eu/system/files/2016-11/2015-10_annex15_0.pdf)与[修订征求意见页](https://health.ec.europa.eu/consultations/stakeholders-consultation-eudralex-volume-4-good-manufacturing-practice-guidelines-chapter-4-annex_en)。 |
| 美国 21 CFR Part 11 与相关基础规则 | 先判断哪些电子记录、电子签名或电子提交落入范围，并识别规定这些记录的基础规则（predicate rules）。闭合系统控制见 `11.10；药品生产相关计算机设备的控制另见 `211.68。参见[`11.1 适用范围](https://www.ecfr.gov/current/title-21/chapter-I/subchapter-A/part-11/subpart-A/section-11.1)、[`11.10](https://www.ecfr.gov/current/title-21/chapter-I/subchapter-A/part-11/subpart-B/section-11.10)、[`211.68](https://www.ecfr.gov/current/title-21/chapter-I/subchapter-C/part-211/subpart-D/section-211.68)和 [FDA 范围指南](https://www.fda.gov/regulatory-information/search-fda-guidance-documents/part-11-electronic-records-electronic-signatures-scope-and-application)。 |
| ISPE GAMP 5 第二版 | 提供按风险管理 GxP 计算机化系统的行业方法，可用于设计验证策略；其地位是行业指南，不能替代适用法规。参见 [ISPE 的 GAMP 说明](https://ispe.org/topics/gamp)。 |

GxP 是各类质量管理规范的统称。临床试验、药物警戒和经营环节要按业务和目标市场另行判定适用依据：

- 中国药物警戒系统可对照[《药物警戒质量管理规范》](https://www.beijing.gov.cn/zhengce/zhengcefagui/qtwj/202204/t20220407_2656162.html)第 30 条，核对系统如何确认适用于预定用途、如何记录全程管理活动。欧盟项目可参照 [EMA GVP Module I](https://www.ema.europa.eu/en/documents/scientific-guideline/guideline-good-pharmacovigilance-practices-module-i-pharmacovigilance-systems-and-their-quality-systems_en.pdf)。
- 中国药物临床试验系统可对照[2026 年修订的 GCP](https://yjj.sh.gov.cn/qtgzwj/20260608/89cbf084b5cb4eab8fd0fb56d8538a1d.html)和[药审中心《药物临床试验计算机化系统和电子数据指导原则》](https://www.gbacdei.org.cn/dwq/news/details/2118510771414634496?colunmId=1466978368401793026&singlePage=true)。指导原则第三章第四节给出了按版本记录测试、取证和保留失败结果的具体写法，其适用范围是临床试验。

## 二 用一条证据链组织验证文件

先写清**需求 → 风险与控制 → 确认或验证用例 → 执行证据及偏差 → 结论**。一个文包可以拆成多份，也可以在批准的计划里合并适合共用的活动；关键在于证据能定位到所覆盖的需求和风险。下表是常用文包，不是每个项目的固定文件清单。

| 文件或活动 | 写清什么 |
| --- | --- |
| 验证计划（VP） | 预定用途、范围和排除项、适用依据、环境策略、分工、交付物、阶段进入和退出条件、偏差处理及放行标准。企业级验证总计划可另用 VMP 管理多个项目。 |
| 用户需求规格（URS） | 为每条需求分配稳定编号，写明使用角色、触发条件和可观察行为。明确数据来源、限制及异常时的结果；用可判定的条件代替“支持”“正常”等模糊承诺。 |
| 风险评估（RA）与配置规格 | 把风险写成“失效情景 → 影响 → 控制 → 如何验证 → 残余风险”。版本、配置、角色、接口和数据流要能对应验证环境；供应商已有证据要核对覆盖范围及版本，差异须补证。 |
| 安装确认（IQ） | 对照已批准的部署基线核对安装和配置，例如软件版本、依赖、服务、时钟及连接配置。记录实际观测值及证据，项目按范围确定核对内容。 |
| 运行确认（OQ） | 验证功能、边界和控制是否按要求运行。覆盖授权与未授权、异常输入、接口失败或恢复等有风险的场景。 |
| 性能确认（PQ） | 由代表性用户按批准的标准操作规程（SOP），在具有代表性的环境和条件下完成实际工作流程，证明系统可支持预定用途。PQ 不等同于做一次压测，也不能把工艺验证的批次数套到软件系统。 |
| 需求追溯矩阵（RTM） | 至少能从 URS 找到关联风险、用例、执行及偏差，也能从一次失败反查影响哪些需求；未覆盖项需说明理由和处置。 |
| 验证总结报告（VSR） | 汇总已执行和未执行范围、实际结果、偏差及复测、残余风险、未完事项和建议使用边界；关联放行决定及其前提。 |

IQ、OQ 和 PQ 回答的问题不同。合并用例或复用供应商、自动化测试、用户验收（UAT）证据时，要说明执行版本、配置、角色及环境为何可用于本项目，并补测关键差异。项目规定审批与取证后再赋予验证效力，不能仅复制原记录的通过结论。[中国《确认与验证》附录第 6 至 18 条](https://www.tid.gov.hk/en/tradecircular/files/2015/ci2015512a.pdf) · [EU GMP Annex 15 第 2、3 节](https://health.ec.europa.eu/system/files/2016-11/2015-10_annex15_0.pdf)

## 三 方案、执行记录和报告分别怎么写

1. **方案先定条件。** 写明文件编号和版本、目的、适用范围、引用文件及其版次、执行环境、系统版本和配置、角色、数据准备、步骤、预期结果、取证要求及接受准则。执行前按质量体系审核批准。双语项目要核对两种语言的动作、阈值、例外和预期是否一致。
2. **每一步都要能判断。** 写“用录入角色保存修改后，系统拒绝且原值不变”，比写“验证权限正常”更清楚。正向操作验证功能可用，反向操作验证限制有效；按钮变灰不足以证明服务端没有保存，需重读记录或查受控的审计数据。
3. **执行后填实际结果。** 待执行方案中不预填实际值、通过状态、签名或执行日期。执行时记录角色、时间、实际观察到的行为和证据编号。截图、记录导出或审计数据应能回到用例、步骤和环境；更正记录时保留原值和更改痕迹。公开示例只用模拟数据，正式验证证据留在受控环境。
4. **偏差与复测留两份证据。** 实际结果偏离预期或执行偏离已批准方案时，记录原结果、影响范围、调查和处置。对修订后的版本按批准方式复测，注明运行号和新证据；复测通过不能覆盖首次失败。对影响后续活动或放行的偏差先评估，符合条件的阶段性批准须说明依据、限制、责任人和期限。
5. **报告说明允许怎样使用。** 按预定接受标准汇总结果，明确验证对象、允许用途和仍适用的限制。例如“本次仅覆盖单站点及所列接口，未纳入跨站点迁移”。由企业规程指定的授权人员审核并作放行决定。文件修订和签署要进入受控流程，不能以一份通过截图替代。

这些写法对应中国 GMP 正文第 147 至 148 条、第 154 至 161 条及《确认与验证》附录第 6 至 10 条；欧盟项目也可对照 [EU GMP Chapter 4 文件管理](https://health.ec.europa.eu/document/download/104b3eb8-81a7-4858-9419-cb06562adb66_en?filename=chapter4_01-2011_en.pdf) 和 [Annex 15 第 2 节](https://health.ec.europa.eu/system/files/2016-11/2015-10_annex15_0.pdf)。

## 四 模拟示例：从需求写到用例和偏差

场景：电子质量记录提交后，只有获授权的人员可更正；复核员需要看得到更正经过。以下编号和内容均为示意，不是正式验证记录。

| 关联项 | 示例内容 |
| --- | --- |
| `URS-001` | 已提交记录不得被普通录入角色修改；授权人员更正时必须填写原因，审计追踪记录操作者、时间、旧值、新值和原因。 |
| `RA-001` | 未授权或未留痕的修改可能使复核基于错误数据。用服务端权限及留痕控制降低风险，分别验证拒绝、批准更正和复核可见性。 |
| `OQ-001` 验证控制 | 在受控环境用录入角色尝试将已提交记录由 7 改为 8，预期拒绝，重读仍为 7。再用授权角色不填原因尝试，预期拒绝且值不变。带原因重试，预期更新为 8，生成一条可追溯的更正记录。取拒绝结果、重读值及审计记录为证。 |
| `PQ-001` 验证流程 | 受训人员按 SOP 在代表性环境完成录入、提交、授权更正、独立复核。预期复核人可按记录编号查到生效值和修改经过，并能完成其获授权的复核步骤。 |
| 模拟执行观察 | 若实际观察为“值更新为 8，但审计记录没有原因”，判为失败并关联偏差 `DEV-001`；保留当次审计记录和执行证据。查明影响并整改后，用独立运行记录复测授权更正及关联回归。 |
| 放行标准 | 关键控制有充分证据，偏差已评估并按质量体系处置，授权人员已审核结论。上述关键缺陷未得到控制时，不能把该用途判为已验证。 |

## 五 上线以后怎样保持验证状态

重点控制按用途和风险选取。权限要覆盖实际数据和操作范围，关键更改要能归属并可复核，备份要验证能恢复，迁移要对照关键数据的值与业务含义。电子签名先判定在该流程是否适用；登录身份、任务确认和普通操作日志本身不足以证明符合电子签名要求。不适用时记录依据和实际批准方式，不以 `N/A` 代替判断。

软件升级、配置与角色变化、接口改动和数据迁移前，评估影响并确定回归或再验证范围。定期结合偏差、变更、权限、审计、恢复演练、支持状态与记录可读性复核系统。退役或更换系统时，验证归档记录及相关元数据在保存期内可检索、可读并可追溯。[EU GMP Annex 11 第 4.8、7、9 至 12、14、16 至 17 节](https://health.ec.europa.eu/system/files/2016-11/annex11_01-2011_en_0.pdf)

数据完整性常用 ALCOA+ 帮助检查记录是否可归属、清晰、同步形成、原始且准确，并兼顾完整、一致、持久和可获得。应用到验证文档，审阅者应能从任一结论找到原始执行记录，从任一异常查到影响的需求和最后的处理决定。[PIC/S 数据管理与完整性指南 PI 041-1](https://picscheme.org/docview/4234)
